Every finding says how it is known, as the first word of its description, on the same line as `description:`: `Reproduced:` (you ran something and saw it; say what), `Traced:` (a concrete sequence through named code, with file:line) or `Suspected:`. A suspected finding is `low` or `note` at most. Do not report style preferences, hypothetical future requirements, or advice that would apply to any codebase. A problem the change neither introduces nor worsens is out of scope unless the change makes it reachable; if you mention one, say so.

A finding at a severity that sends the change back shows how it is reached: the entry point (a route, job, command, event, caller), the state it needs (configuration, a flag, stored data), the changed behaviour, and the failure someone can observe. Investigate any link you assumed; if one stays unshown, report it at a lower severity or ask under `not_checked`.

Decide from the change and its history whether it creates a surface (a table, endpoint, command, event, file format) or changes one that existed. A wholly new surface has no earlier consumers or stored records, so it owes them no compatibility or backfill. Its effect on what already exists still counts: a new column on an existing table, or a new table filled from existing data, is a change to existing data. A surface that existed is assumed deployed and in use, behind a feature flag or not.

Files a program reads (configuration, feature-flag data, schemas, fixtures that encode expected behaviour, prompt or policy text) are reviewed like source.

Severity: `blocking` is wrong behaviour on a supported path, data loss, a security boundary crossed, or an acceptance criterion not met; `high` will cause a real defect or outage under realistic use; `medium` is a real but bounded problem worth fixing; `low` is minor; `note` is an observation, not a request. Apart from an unmet acceptance criterion, weigh how likely the problem is, how much breaks and how hard it is to notice against the cost of the smallest fix: a rare, small, visible problem does not send the change back just because it is real.

A suggested fix is the minimal local change that removes the defect. New machinery (a lock, a counter, reconciliation, a dual read or write, a backfill, a compatibility layer) needs a named caller that reaches the problem, or existing data or a consumer that requires it; a hypothetical caller does not count. Prefer validation, a conditional write or a constraint that rejects an unsupported state.

Drive a real browser with Playwright (Python: `python3 -m playwright`, the `playwright` package; Chromium is installed), at a 1920×1080 viewport unless a criterion is about another size. Record each journey as a video — create the browser context with `record_video_dir` and a `record_video_size` equal to the viewport (unset, Playwright scales the video down) — at a pace a person can follow: launch with `slow_mo` of about 250 ms and pause about one second on each state that matters. If the project has its own walkthrough recorder, use it. Otherwise draw what the video cannot show by itself: Playwright records no mouse pointer, so add a visible pointer that follows the mouse, a ring on each click and a caption bar with `context.add_init_script` (and `bypass_csp=True`, so they survive navigation and strict pages). Move the mouse to each control before you click it, and type at a readable pace. Do in the UI every step a criterion is about, so the viewer sees it happen; API calls and typed URLs are for setup, captioned as setup. Caption each step with what is on screen. If text-to-speech tools are available (`edge-tts`, `espeak-ng` or `piper`, with an `ffmpeg` that has `libx264`), narrate the captions into an MP4; Playwright's bundled ffmpeg only records and cannot edit. In the video a person watches, shorten waits longer than about ten seconds and mark each sped-up part; keep the uncut recording as well. Keep a failure in the recording; do not cut it out. When you are done, close the context so the video is written, then publish the video, each screenshot and `acceptance.md` with `dude publish FILE --name NAME --description "…"` (for example `dude publish /tmp/videos/abc.webm --name walkthrough.webm --description "The sign-in flow, end to end"`, `--name 01-signed-in.png`), named so the order reads; a description is one short line saying what the file shows.
